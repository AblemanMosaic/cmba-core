# CMBA Core + Workbench — complete I–L construction program

Standing: an engineering program, not authority to publish, deploy, upgrade a customer,
execute an arbitrary payload, or claim independent approval. Four maximum-batched construction
turns are targeted, including Batch I. External review and target-host validation are separate
legs; they do not disappear to make the turn count smaller.

## End state and scope

Deliver a separately installable CMBA library, an optional native Python workbench, bounded
application evaluators and compatibility adapters, a data-only application inventory, frozen
conformance specifications, constitutional contracts and realization bindings, and one complete
reviewable source/evidence package. The DKN Batch H source ZIP and wheel remain immutable.

“All applications in place” has three different meanings, recorded separately for every entry:

1. Existing code, where actually available: pin it, describe it, integrate through an adapter,
   and execute its existing verification cases. DKN is the supplied implementation here.
2. Application families described by research: give each a versioned contract, explicit inputs,
   verification predicates, authority/effect boundary, resource budget, failure cases and a
   bounded demonstrator. A demonstrator is not the entire envisioned application.
3. Domain instantiations in the historical taxonomy: preserve the exact name, dimensions and
   use case; supply an inspectable template and route it to relevant common capabilities.
   Do not claim that a generic record template implements a regulator, clinical system,
   election protocol, legal decision-maker or other domain validation.

Operational weapons/nuclear command systems are not part of this program. Their historical
catalogue labels remain descriptive records only. No medical/election security or regulatory
compliance is inferred from a successful commitment check. The program does not reproduce
unsupported historical performance, zero-hallucination, commercial, patent or deployment claims.

## Batch I — foundation, recovered inventory, executable bridge (this batch)

**I.1 Custody and source recovery.** Verify Batch H's exact source/wheel hashes; retain both plus
its external receipts. Re-execute the inherited v0.2 suite without changing the baseline.
Retrieve primary source material where available; inventory missing papers and conflicting
terminology instead of pretending a review of them occurred. Preserve direct source text and
separate engineering mappings from source claims.

**I.2 Architecture.** Specify Core → profiles → evaluators → workbench → host enforcement as
separate responsibilities. Resolve aggregate hash terminology by role, without equating
application-specific constructions. Adopt open-ended dimension names and finite objects.
State exactly which older assumptions are not carried forward.

**I.3 Executable core.** Standalone finite canonical encoding, typed dimension commitments,
versioned binding bodies/roots, typed references, deterministic inspection and comparison,
closed profile/capability descriptors, evaluation-context commitments and replayable receipts.
No core dependency on DKN, a GUI, a network, UCM or an institutional authority.

**I.4 Demonstrators and interface.** Frozen-DKN manifest and archive adapter; one actually
recomputed CHC canonical-JSON transformation; GenDev quoted-source-span and attribution
checker. Data-only catalogue for all recovered applications. Native read-only workbench with
explicit demonstration context selection, a command-line JSON interface and library APIs.

**I.5 Evidence.** Tests for structural mutations, ambiguous encodings, wrong transforms,
source-span substitutions, rehashed forged results, false profile registration, unknown critical
dimensions, effect attempts and self-supplied pins. Source-bound contract/realization maps,
portable core vectors, installed-wheel smoke, UI smoke, fresh-extraction replay and deterministic
packaging. Batch I is not public protocol ratification.

**Exit:** the core runs without DKN; DKN retains its exact identities; at least two different
application predicates use the same binding/evaluation path; unimplemented applications remain
visible and noncallable. Every claimed result has replayable evidence or an explicit limit.

Implement the application-family layer in one integrated batch, sharing schemas and predicates
rather than building fifty-two unrelated engines. Preserve I1 bytes; corrections require a
versioned compatibility decision and retained failure evidence.

CMBA-native signing/endorsement support is a J obligation: binding body first (including required
endorsement policy), signatures over an unambiguous typed payload second, optional envelope hash
last. This does not alter the unsigned I1 binding root. Reject inadmissible keys, signature
substitution and circular constructions. Reuse reviewed primitives; do not invent crypto.

**Exit:** each inventoried family has an operational, bounded evaluator or an explicit
reference-only disposition. Joint demo: session → transform → DKN object → scoped approvals →
selective view → evaluation receipt. The same object must receive different scoped assessments
when evidence/time/policy changes, without rewriting its history. No network deployment claimed.

## Batch K — integrated workbench and controlled local workflows

Native workbench pages: object/dimension inspector; application and capability browser;
provenance and relationship navigation; exact comparison; jurisdiction/consent matrix;
receipt history and replay; disclosure preview; finite profile-design explorer; toolchain and
realization qualification view. Statuses, missing inputs, contradictions and truncation must be
visible rather than compressed into a green badge.

Separate authoring from reading. Add explicit user-selected local save/export and data-import
operations. Bind effect requests to target, input root, policy/context and proposed output; show
those facts before approval. Define cancellation, expiry, replacement detection, path confinement
and file-overwrite rules. Host enforcement is a real separate mechanism, not a field inside a
manifest. No silent install, network fetch, shell execution, trust-store update or publication.
Where a selected local transformation requires an executable, use a separately approved adapter
with explicit resource limits; a host process is not a security sandbox merely because it has a
receipt. Untrusted profile data cannot provide an import path.

Provide Python APIs, JSON/CLI parity, keyboard navigation, errors and responsive bounded jobs.
Persist explicit workspace state only under user-owned locations, not inside loaded objects.
Add DKN/CCP/UCM/P/PPI/Courthouse handoff formats without claiming operational host integration.
A finite design-space explorer reports supported/unsupported combinations and evidence
obligations; it does not infer security from enumerating combinations.

**Exit:** all bounded application-family workflows are usable through one interface without
learning their implementation language; core use remains possible without the UI. Native UI
behavior is tested where an actual display is available, with target-host limits stated.

## Batch L — consolidated qualification and frozen handoff

No feature expansion. Audit the full source/model/schema/capability/result correspondence;
attack parser, signature, profile and receipt substitution, effect boundaries, resource limits,
disclosure leaks, approval overlaps, stale pins and cross-profile laundering. Freeze a shared
conformance corpus and exercise a separately written small-core verifier in another language.
Compare exact typed canonical results, not loose host-language equality. A bounded corpus is
not whole-program equivalence. Qualify adapters separately from the shared core.

Replay DKN's preserved suites, new application suites, all UI and headless workflows and current
contract checks. Produce installable core/workbench packages, an exact current release envelope,
SBOM/dependency inventory, deterministic source and wheel builds, migration/rollback instructions,
claim and source registers, acceptance reconciliation, defect history, operator commands and one
independent-review dispatch. Only actually executed environments receive PASS.

**Exit:** frozen engineering candidate with reconciled documentation and all local claims backed
by current evidence. A mandatory unavailable leg blocks its corresponding gate; it is not
silently made optional. Public release and independent acceptance remain separate decisions.

## External and intentionally separate gates

Native Windows/WSL/macOS replay; genuine legacy BLAKE3 when unavailable; fresh package resolution;
real key custody and revocation/freshness inputs; actual external-floor protection; independent
security review; live storage/federation/network deployments; domain-specific operational approval.
The source archive includes replay instructions, not invented results for these gates.

## Turn economy and continuity

Four build turns: **I → J → K → L**. Batch I is executable foundation, not an additional
planning-only turn. Each successor consumes the preceding exact archive and updates one
cumulative program ledger, decision register, source register, acceptance matrix and claim map.
Do not ask the user to re-answer choices already fixed here. Reopen a batch only for a concrete
finding, not to keep widening the feature list. Preserve version sovereignty: adoption is explicit,
existing namespaces and DKN roots are never silently migrated, and no profile is force-enabled.
